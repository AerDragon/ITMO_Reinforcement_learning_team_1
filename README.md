## Карточка проекта

### Исследовательский вопрос

Насколько часто и на каких типах мутаций штатные тесты MBPP на `sanitized/test` расходятся с эталоном неверности (пропускают мутант, неверность которого доказана тестом-контрпримером), и как эта частота зависит от свойств задачи — типа ответа и наличия краевых входов в тестах?

### Данные и срез

- **Датасет:** MBPP, [`google-research-datasets/mbpp`](https://huggingface.co/datasets/google-research-datasets/mbpp) на Hugging Face.
- **Конфигурация и срез:** конфиг `sanitized`, сплит `test` — 257 задач на Python, у каждой эталонное решение и обычно 3 `assert`-теста. Берём все задачи сплита, мутанты пишем для 150 задач, отобранных случайно с seed 42.
- **Лицензия:** CC-BY-4.0.
- **Загрузка:** `load_dataset("google-research-datasets/mbpp", "sanitized")`.


### Свойства задачи (как считаем)
 
- **Тип ответа:** запускаем эталонное решение на входах из `test_list` и берём `type(...)` возвращаемого значения. Если у задачи на разных тестах разные типы, то категория `mixed`. Для анализа объединяем в группы: `int`, `float`, `bool`, `str`, `list/tuple`, прочее (`dict`, `set` и т. п.).
- **Покрытие краевых случаев:** аргумент теста считаем краевым, если это `None`, число ≤ 0, или строка/список/кортеж/словарь/множество длиной ≤ 1. Свойство задачи: число `assert`-ов, в которых есть хотя бы один краевой аргумент (0, 1, ≥ 2); в анализе используем бинарный признак «есть хотя бы один краевой тест».

### Эталон и метод

- **Эталон (прокси):** неверность по построению — мутанты эталонного кода: сдвиг границы, замена оператора, пропуск крайнего случая, хардкод ответов из тестов. Для каждого мутанта пишем свой тест-контрпример, на котором он падает, а эталон проходит.
- **Хардкод ответов из тестов** — отдельная контрольная группа, не тип мутации: такой мутант проходит все `assert`-ы по построению. Генерируем его для каждой из 150 задач, показываем отдельной строкой и в общую долю ложных пропусков не включаем. Его доля пропусков должна быть 100%.
- **Что эталон не покрывает:** ошибки, которых мы сами не придумали, и качество кода сверх корректности.
- **Оцениваемый оценщик:** прогон штатного `test_list` — решение считается верным, если прошли все `assert`-ы задачи.
-  **Базовое сравнение (на срезе `test`, 257 задач):** эталонные решения проходят 257 из 257, заглушка `return None` — 0 из 257. То есть оценщик не отвергает верный код и ловит грубо неверный.

### Метрика и критерий

- **Объём:** целевое число 300 мутантов в основной метрике: по 2 мутанта на каждую из 150 задач, типы чередуются так, чтобы на каждый из трёх типов пришлось около 100. Плюс 150 мутантов-хардкодов в контрольной группе.
- **Метрика ошибки:** доля ложных пропусков = число мутантов, прошедших все штатные тесты / число всех мутантов (без хардкода); с 95% интервалом Уилсона, отдельно по типам мутаций.
- **Контроль ложных отказов:** эталоны, упавшие на тестах / все эталоны.
- **Численный критерий:** говорим «штатные тесты пропускают неверный код», если нижняя граница 95% интервала Уилсона для доли ложных пропусков выше 5% на 300 мутантах основной метрики (минимально допустимый объём — 150, если пилот покажет, что 300 не успеваем). Ниже 5% тесты на этом срезе ведут себя почти как оракул.
### Риск и границы

- **Возможная ошибка оценщика:** высокий балл без решения задачи — код, который подставляет ответы на три тестовых входа, или решение, верное только на «удобных» входах из тестов. Обратная ошибка — отказ верному коду из-за формата: `list` вместо `tuple`, другой порядок элементов, `float` без допуска.
- **За границами проекта:** не обучаем и не дообучаем модели, не генерируем решения языковыми моделями, не сравниваем методы между собой, не берём второй датасет (MBPP+, HumanEval) и другие языки программирования.
